## Diagnóstico de 503 e créditos

1. Selecionar ambiente e deployment corretos, abrir os detalhes completos da requisição e consultar `failureKind`. A listagem pode mostrar apenas o primeiro `cache_miss` da invocação.
2. `quota_denied` é negação do orçamento interno antes do fetch. `upstream_rate_limited` é um 429 do provedor; Redis, rede, timeout e payload inválido têm categorias próprias. Não atribuir todo 503 à mesma causa sem o evento correspondente.
3. Conferir no painel os custos e tetos efetivos, o escopo Preview e os overrides da branch. 1.000 créditos representam uma unidade de chamada ponderada, não 1.000 pedidos HTTP. Busca, previsão e deployments no mesmo Redis compartilham a reserva.
4. A contabilidade usa janelas móveis de minuto, hora, 24 horas e 31 dias. Um hit válido não reserva novos créditos; um miss pode voltar a funcionar quando reservas antigas saírem da janela. Redeploys e limpeza de cache climático não zeram esse consumo.
5. Alterar tetos de teste somente em overrides da branch Preview e redeployar a API depois. Uma variável geral compartilhada por Production/Preview usa o mesmo valor nos dois ambientes. Preservar as margens e medir o consumo Redis antes da política final de produção.

### Cache Redis integrado localmente na P6

O adapter de cache está ligado às duas rotas da entrada Function. Ele deriva chaves opacas com HMAC-SHA-256 de `CACHE_HMAC_KEY`, mantém namespace e versão, valida os valores na leitura e gravação e aceita no máximo 24 KiB por entrada. A resposta Redis REST é limitada a 64 KiB. O TTL máximo é de 24 h para busca e 10 min para previsão; não há valor vencido nem erro em cache. A entrada exige o segredo, distinto de `RATE_LIMIT_HMAC_KEY`, sem valor no repositório ou no projeto web. O fluxo de desenvolvimento local mantém o cache em memória.

Misses concorrentes usam um lock Redis de 12 s com token, [`SET` com `NX`/`PX`](https://redis.io/docs/latest/commands/set/) e liberação condicional. Outras instâncias aguardam até 6,3 s em leituras espaçadas; depois podem carregar por conta própria. Cada chamada real ao provedor continuará exigindo a reserva da P3. Em P1b/P1c, verificar a semântica no Redis real e usar amostras representativas de hit, miss e negação para estimar comandos mensais com margem no Free.

### Limite por visitante implementado localmente na P5

A entrada Function exige um único IP válido em `x-vercel-forwarded-for` para rotas diferentes de `/health`; cabeçalho ausente ou ambíguo resulta em `503` seguro. O código ignora `x-forwarded-for` para identidade. A [Vercel documenta](https://vercel.com/docs/headers/request-headers) os cabeçalhos encaminhados, mas a confiabilidade no acesso direto e via rewrite precisa ser provada em P1d com pedidos falsificados. `/health` não consulta Redis.

O IP é normalizado (IPv6 por prefixo /64) e transformado em HMAC-SHA-256 com `RATE_LIMIT_HMAC_KEY` e minuto UTC; o IP bruto não entra em logs ou chaves Redis, e o digest aparece apenas em chaves opacas temporárias, nunca em logs. A mesma variável já prevista na tabela acima atende à P5, sem configuração adicional agora. O pré-limite por instância, antes de Redis, mantém no máximo 2.048 identidades de um minuto e aplica 60 pedidos gerais, 30 de busca e 15 de previsão. A capacidade cheia nega novos visitantes naquela instância até a próxima janela. O Redis aplica os mesmos tetos de modo atômico entre instâncias, com TTL até o fim do minuto; falha do Redis nega o pedido com `503`, limite excedido retorna `429`. O script usa [bloqueio por chave da Upstash](https://upstash.com/docs/redis/features/key-locking); sua execução foi observada no Monitor em 2026-10-10, mas as provas completas de contenção e falha real ainda dependem de P1b/P1c.

Esses contadores usam janelas fixas de minuto; medir rajadas na fronteira e o custo de comandos por pedido em P1c. A regra WAF antes da Function continua obrigatória na P7/P1c e deve cobrir tanto o domínio direto da API quanto o rewrite do web. Registrar na prova P1 apenas categorias e contagens, nunca IPs ou digests.

### Roteamento, cache e WAF da P7

No projeto web, deixar `VITE_API_BASE_URL` **sem definir** em Preview e Production. O cliente chama caminhos relativos `/api/v1/*`; o build rejeita um valor HTTP, loopback ou de origem diferente do próprio web. Um valor HTTPS da própria origem é aceito, mas desnecessário. `API_ORIGIN` é a URL do projeto API usada somente pela configuração do rewrite; verificar na configuração efetiva do Preview que ela corresponde à API Preview daquele deploy. O web não define fallback de SPA, de modo que `/api` e `/api/*` sempre passam pelo rewrite. Confirmar query, método, status, envelope de erro e 404 JSON em P1a.

Os cabeçalhos do web aplicam CSP com `connect-src 'self'`, HSTS, política de referer e `nosniff`. O atributo de estilo inline é permitido somente para a imagem de fundo escolhida pelo React; scripts inline não são permitidos. `/`, `index.html` e arquivos públicos sem hash revalidam. Somente arquivos em `/assets/` com hash Vite de oito ou mais caracteres usam `immutable`. API direta e respostas da Function definem `Cache-Control: private, no-store` e `Vercel-CDN-Cache-Control: no-store`; o rewrite web também define `Cache-Control: private, no-store` e `x-vercel-enable-rewrite-caching: 0`. A [mudança de 2026 no cache de rewrites externos](https://vercel.com/changelog/vercels-cdn-now-respects-cache-control-headers-from-external-origins-by-default) torna a medição do CDN em P1a obrigatória mesmo com esses cabeçalhos.

A [regra de rate limiting do WAF](https://vercel.com/docs/vercel-firewall/vercel-waf/rate-limiting) é configurada manualmente no painel **de cada projeto**: Request Path Equals `/api` **OR** Request Path Starts with `/api/`, chave somente IP Address, janela Fixed Window de 60 s, limite inicial de 60 pedidos e ação Too Many Requests (429). São duas regras, uma no projeto web e outra no projeto API. O valor 60 é provisório, alinhado ao limite geral da aplicação; P1c verifica bloqueio e uso do plano antes de confirmar ou ajustar. Usar Firewall → Rules → Project rules → Add Rule, preencher as condições unidas por OR e a ação Rate Limit; salvar, revisar em Review Changes e publicar. Uma regra habilitada no formulário pode ainda estar pendente de publicação; conferir a confirmação de aplicação. Isso não equivale a retirar a proteção do deployment. No Preview protegido, verificar bloqueios nos caminhos direto e reescrito, ausência de invocação da Function e de comandos Redis. Se o rewrite não passar pelos controles como esperado, revisar a topologia em P0; a existência da regra não basta como prova.

### Medição de cache e consumo

1. Em Preview protegido e com consultas reais limitadas autorizadas, ativar Monitor sem filtro e registrar horários/status de uma busca válida sem cache e sua repetição. Selecionar a cidade e separar a requisição de previsão de qualquer busca anterior. Não limpar Redis, mudar chaves ou ampliar a cota para forçar misses.
2. Recarregar a página com a mesma cidade antes do TTL da previsão. Conferir leitura da mesma chave no ambiente privado e ausência de nova reserva, lock e gravação. Comparar `retrievedAtUtc`, registrando só igualdade ou mudança, sem corpo meteorológico ou localização. A recarga é um estímulo válido, assim como reabrir pelo logo, desde que a requisição de previsão esteja identificada.
3. Após o TTL contado da gravação inicial, recarregar uma vez. Esperar cache indisponível, nova reserva, gravação e timestamp posterior; um hit anterior não deve estender o TTL. Registrar horários e não apresentar a consulta posterior como medição do instante exato da expiração. Busca tem TTL de 24 h e precisa de ensaio separado.
4. Na [amostra de 2026-10-10](preview-waf-redis-2026-10-10.md#perfis-de-cache-e-renovação-da-previsão), busca e previsão tiveram nove registros visíveis por hit e 29 por miss; a previsão foi renovada após o prazo. São contagens do Monitor, incluindo comandos internos Lua. Antes de projetar consumo, conferir nas fontes oficiais da Upstash a unidade aplicada a `EVAL` e seus comandos internos. Não assumir que cada linha ou cada chamada REST corresponde a um comando faturado.
5. Projetar cenários normais e adversariais incluindo chamadas admitidas que terminam em validação/limite, misses, hits, contenção, falhas, circuito e limpeza de reservas antigas. Um WAF por IP não estabelece sozinho um teto agregado de tráfego Redis de todos os visitantes. Conferir limite mensal efetivo, margem, upgrade automático e procedimento de acompanhamento do painel. A reserva Open-Meteo limita saída ao provedor; não comprova o orçamento Redis.

Esse procedimento não substitui contenção entre instâncias, falha fechada nem a medição do corpo bruto de previsão dentro de 64 KiB. Não confundir o payload normalizado no cache com a resposta bruta recebida da Open-Meteo.

## Falha, limites e rollback

- Se Redis falhar, expirar a cota gratuita ou negar reserva, novas chamadas Open-Meteo param. A API responde erro público seguro; `/health` continua a indicar somente que a Function responde. Investigar com contagens/categorias, sem dados de localização ou IP.
- Se a Open-Meteo responder `429` com reserva própria disponível, registrar apenas `upstream_rate_limited`, abrir o circuit breaker compartilhado e interromper novos misses até reabertura controlada. Acompanhar taxa e duração; não fazer retries em massa nem classificar como abuso do visitante.
- Se o teste revelar IP do visitante no eco da saída, interromper o caminho de release, não apontar a API real à Open-Meteo e revisar o adapter/topologia na P0.
- Ensaiar rollback do web e da API para deployments de Preview previamente verificados, preservando chaves/valores Redis versionados. Registrar IDs, ordem, comandos e smoke de ambas URLs no ensaio P11. Compatibilidade com uma versão pública anterior só se aplica depois do primeiro lançamento.
- Publicação pública só após pacote de privacidade, direitos, termos, quota, CI, métricas, Preview e rollback revisto pelo proprietário em decisão separada.
