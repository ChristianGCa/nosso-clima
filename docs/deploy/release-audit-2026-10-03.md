# Auditoria de preparação para publicação — 2026-10-03

**Resultado: publicação e proposta P0 de Worker único bloqueadas.** O proprietário determinou em 2026-10-03 que a Open-Meteo nunca receba o IP do visitante. Este registro distingue fatos observados, fontes oficiais e testes ainda não executados. Nenhum resultado local substitui uma nova emenda P0 aprovada, staging ou a revisão final do proprietário.

## Escolha técnica proposta para a emenda P0

**Candidata recomendada:** um único Worker com handler Fetch, assets estáticos e API na mesma origem, no endereço `nosso-clima.<subdomínio-da-conta>.workers.dev` se o nome estiver disponível. Ele usa uma implantação, dispensa CORS entre site e API e permite o [binding de rate limiting de Workers](https://developers.cloudflare.com/workers/runtime-apis/bindings/rate-limit/). Com roteamento dos assets sem passar pelo script, seus pedidos permanecem gratuitos e ilimitados, enquanto pedidos à API contam na cota diária. [Workers static assets](https://developers.cloudflare.com/workers/static-assets/), [cobrança](https://developers.cloudflare.com/workers/static-assets/billing-and-limitations/). O Free comporta os limites nominais de arquivos e CPU, mas a execução ainda depende das medições P1. Pages com Functions é alternativa se o proprietário voltar a exigir `*.pages.dev`; sua [lista de bindings](https://developers.cloudflare.com/pages/functions/bindings/) não inclui o rate limiting, então exigiria outro desenho para 60/30/15. [Limites Workers](https://developers.cloudflare.com/workers/platform/limits/).

O proprietário aceita considerar a retirada de `Retry-After`/`x-ratelimit-*` sem valores exatos e o uso restrito de `CF-Connecting-IP` se a opção escolhida for a melhor e não introduzir problemas de segurança ou LGPD. Isto é uma condição para a decisão, não aprovação incondicional da mudança de contrato. O spike deve demonstrar proteção suficiente contra abuso, minimização do IP e o tratamento do risco de esgotamento da cota Free.

**Risco novo de privacidade identificado na revisão:** o Node atual cria requisições novas à Open-Meteo sem encaminhar o IP do visitante em cabeçalhos ou parâmetros. Já a [documentação da Cloudflare sobre subrequisições de Workers](https://developers.cloudflare.com/fundamentals/reference/http-headers/) diz que `CF-Connecting-IP` pode refletir o IP do cliente em requisições a destinos fora de uma zona cliente Cloudflare, mesmo sem cópia explícita pelo código. A presença desse cabeçalho no destino Open-Meteo ainda não foi medida. A emenda P0 exige teste controlado em staging e, até prova de ausência, que o aviso trate a Open-Meteo como possível destinatária do IP do visitante. Uma exigência de não transferir o IP requer rever a topologia se a Cloudflare não permitir garanti-la.

O proprietário confirmou que a exigência é **nunca transferir** o IP do visitante à Open-Meteo. A promessa não pode ser feita para o Worker único neste momento. A P0 proposta foi marcada como bloqueada antes de qualquer implementação; o novo desenho deve comprovar que a Open-Meteo recebe somente o IP de saída da infraestrutura e nenhum cabeçalho com o IP do visitante. Aviso de privacidade, base legal ou HMAC de rate limiting não substituem essa garantia técnica. Uma consulta DNS em 2026-10-03 mostrou A records diretos para `api.open-meteo.com` e `geocoding-api.open-meteo.com`; isso não prova, por si só, o tratamento dos cabeçalhos no caminho Worker.

Sem zona própria, a configuração de regras WAF por zona pelo proprietário parece indisponível em `pages.dev`/`workers.dev`; isso é inferência a confirmar no painel, não proteção presumida. Uma inundação de pedidos à API pode consumir as 100.000 invocações diárias compartilhadas do Free, embora o site estático possa continuar acessível. `CF-Connecting-IP` pode ser usado somente como cabeçalho acrescentado pela borda Cloudflare em uma rota que não aceite acesso direto alternativo; não confiar em `X-Forwarded-For`. O rascunho P0 agora requer derivar uma chave HMAC pseudônima antes de chamar o binding, sem persistir IP bruto no D1, rate-limit key, caches ou logs da aplicação. A Cloudflare ainda recebe o IP e seus logs de plataforma precisam ser verificados. O binding de limite responde `success`/falha, sem contagem ou tempo exato de reset; preservar `Retry-After` ou `x-ratelimit-*` com valores fabricados seria incorreto. [WAF custom rules](https://developers.cloudflare.com/waf/custom-rules/), [Rate Limiting API](https://developers.cloudflare.com/workers/runtime-apis/bindings/rate-limit/).

## Contrato de produção ainda divergente

- As duas specs, o mapa e as tarefas agora contêm uma **emenda P0 de Worker único bloqueada** pelo requisito de não transferir IP à Open-Meteo, com o histórico Node arquivado em `docs/history/`. O proprietário autorizou redigir essa proposta e aceitou o risco residual da cota Free, mas a condição de privacidade posterior impede sua aprovação antes de um redesenho. O código atual continua Node/Fastify; nenhum corte foi executado. As APIs públicas, limites de entrada, erros, créditos, privacidade e pisos de `CONSTRAINTS.md` continuam vinculantes.
- `apps/api/src/config/env.ts` aceita origem `http:` em produção; o teste atual a considera válida. `apps/web/src/api/http.ts` usa `VITE_API_BASE_URL` sem validação. Corrigir após definição da origem de produção e testar ausência, HTTP, loopback, divergência e HTTPS permitido.
- Ainda não há cabeçalhos de CSP para o site estático, HSTS ou política de referrer. A política final deve limitar `connect-src` à própria origem, proibir conexão direta à Open-Meteo e ser verificada no E2E com inspeção de rede. O aviso de privacidade deve registrar que a Cloudflare recebe o IP e especificar logs, retenção e transferência conforme configuração real; a retenção de Workers Logs Free é [3 dias](https://developers.cloudflare.com/workers/observability/logs/workers-logs/) nesta consulta, não uma afirmação sobre todos os produtos Cloudflare.
- `test:e2e`, `test:performance`, `.github/workflows/`, `tests/` e Gitleaks ainda não existem. O desempenho precisa medir LCP da primeira visita neutra **e** da visita com cidade restaurada e fundo carregando, além de CLS durante a transição. A execução hospedada depende do remote. Não houve ensaio de rollback nem migração D1 compatível com a versão anterior.

## Uso e privacidade Open-Meteo

Os [termos gratuitos](https://open-meteo.com/en/terms/) consultados em 2026-10-03 estabelecem menos de 600 chamadas/minuto, 5.000/hora e 10.000/dia, uso não comercial e atribuição. O mesmo texto diz que logs do serviço gratuito, inclusive coordenadas, são apagados após 90 dias. A frase do rodapé sobre até 90 dias é compatível com isso. O aviso final deve informar busca enviada à geocodificação, coordenadas/fuso enviados na previsão e na volta do visitante, cidade salva localmente, IP recebido pela Cloudflare, retenção real dos logs configurados, responsável e contato.

Para a preparação do release, **tratar a LGPD como aplicável**: o serviço será oferecido no Brasil e haverá tratamento de IP e dados de localização/busca potencialmente vinculáveis a uma pessoa. A [LGPD](https://www.planalto.gov.br/ccivil_03/_ato2015-2018/2018/lei/l13709.htm) define dado pessoal por identificabilidade, e a [ANPD inclui IP e páginas acessadas em seu próprio aviso](https://www.gov.br/anpd/pt-br/acesso-a-informacao/aviso-de-privacidade). A conclusão operacional não dispensa revisão jurídica do aviso, da base legal e das transferências ao provedor e à Cloudflare antes do lançamento.

Orçamento ainda sem teto demonstrado: `créditos = misses de geocoding + (peso confirmado da previsão × misses de forecast)`. Calcular essa expressão separadamente por minuto, hora e dia para buscas, seleções, retornos automáticos, cache frio, reinícios e pico adversarial; reservar abaixo dos três limites com margem. A estimativa de 100 usuários/dia não define pico ou número máximo de consultas. Limite por IP, cache local e 100.000 invocações/dia da Cloudflare não garantem a cota agregada da Open-Meteo.

## Gates executados e falhas preservadas

Ambiente: Node `24.21.0`; npm instalado no host `11.19.0` e npm `12.0.2` obtido para corresponder ao projeto. O `npm ci` **na árvore de trabalho** falhou inicialmente com `ENOTEMPTY` ao remover `node_modules/@rolldown/binding-linux-x64-gnu`, inclusive com npm 12. Um checkout limpo extraído do `HEAD` em `/tmp/nosso-clima-release-audit-20261003` recebeu `npm ci` com npm 12: passou, 192 pacotes, zero vulnerabilidades. Os comandos `check`, `test:coverage` e `test:a11y` da árvore de trabalho falharam em seguida por binários ausentes após a instalação interrompida. O audit inicial falhou por DNS do sandbox; repetido com acesso de rede, passou com zero vulnerabilidades. Após guardar os módulos antigos, `npm ci` com npm 12 passou também na árvore de trabalho, adicionando 192 pacotes. Um servidor Vite local mantinha um binário antigo aberto; com autorização do proprietário, foi encerrado e a pasta de módulos antigos em quarentena foi removida.

Com npm 12, `npm run check`, `npm run test:coverage`, `npm run test:a11y` e `npm audit --audit-level=high` passaram **na árvore de trabalho final**: API 363 testes/19 arquivos, web 73 testes/7 arquivos, limites de importação aprovados e zero vulnerabilidades no audit. Cobertura API: statements 94,9%, branches 91,79%, functions 95,33%, lines 97,84%. Cobertura web: statements 96,73%, branches 88,7%, functions 97,4%, lines 98,89%. O gate axe cobriu estados neutro, busca, carregamento, erro, sucesso, cidade restaurada e dez fundos em mobile/desktop, com contraste mínimo observado de 8,26:1 nos controles. A primeira tentativa de axe no sandbox falhou ao escutar `127.0.0.1:4175` (`EPERM`); essa falha não é um achado de acessibilidade. `git diff --check` e a comparação entre `LICENSE` e `apps/web/public/code-license.txt` passaram.

Esses resultados não incluem E2E, performance, Gitleaks nem CI hospedado, que ainda não estão implementados. Não há evidência de publicação aprovada.
